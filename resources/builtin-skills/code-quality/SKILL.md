# 编码习惯

## 动手之前先查

1. **先找现成的**，别急着新建文件或函数。按这个顺序找：
   - **优先用已接入的代码索引工具**：如果 MCP 里配了语义索引 / 引用查询类工具（Serena、GitNexus、IDE/LSP 类），先用它们查「这个功能/符号在哪定义、被谁引用」——比文本搜索准。
   - 没有这类工具时，再用文本搜索（`grep -rn` / 编辑器搜索；按项目实际语言选扩展名过滤，不要只盯某一种）按关键词找同名、同功能的实现。
   - 读懂 2–3 个同类文件的写法，照着来（命名、目录位置、错误处理、文案都要一致）。
2. **改公共代码之前**（被多处引用的组件 / 工具函数 / 类型 / 常量），必须先查一遍引用：
   - 有索引工具就用它查引用；没有再用 `grep -rn "符号名" --exclude-dir=node_modules --exclude-dir=dist --exclude-dir=target --exclude-dir=build`（按项目实际语言加 `--include`，不要只盯某一种）
   - 把所有调用点列出来，逐个确认这次改动不会破坏它们；确认不了就先问用户，别赌。
3. **读项目规则**：仓库根的 `AGENTS.md`、各级目录的规则文件里写明的约定（命令、目录边界、测试要求、i18n 规范）必须遵守，不是建议。

## 写的时候

- **复用优先**：能调已有函数就不新写；能加一个可选参数就不加新函数；能扩展现有组件就不复制一份出来。
- **简洁**：
  - 不写没人调用的抽象，不写"将来可能用到"的参数
  - 不写多余的 `if` / `try` —— 让错误自然抛出，除非有明确的处理动作
  - 不写解释显而易见的注释（`// 返回列表` 这种删掉）
  - 注释只写「为什么」，不写「是什么」
- **一个改动一个目的**：不顺手重构无关代码，不顺手改格式，不顺手删别人的注释。

## 改完自检

1. 类型检查 / 编译必须过（用项目自己的命令，不假设是哪种语言或构建工具）
2. 项目自己的 lint / 静态检查必须过
3. 改了哪个模块就跑对应测试；新增逻辑补一条测试
4. 汇报时写清四件事：改了哪些文件、为什么这么改、有没有影响到别处、验证了什么

## 不要做

- 为了"看起来更完整"写一堆用不上的代码
- 没查引用就改公共类型 / 公共组件的签名
- 跳过验证就说"改好了"
- 猜测 API：不确定某个函数存不存在，先查（索引工具 → 搜索 → 读文件）确认，别凭印象写
